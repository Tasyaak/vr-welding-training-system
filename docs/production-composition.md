# Production coordinator setup

`ProductionTrainerBootstrap` is the only production composition root. It creates one
`ProcessCoordinator`, disables the prototype demo, and deliberately keeps activation
inhibited when a real provider is absent.

## Unity scene setup

1. Open `Assets/Trainer/Scenes/Bootstrap.unity` in Unity 6.3 LTS and allow scripts to compile.
2. Select `AppRoot/Application/TrainerBootstrap`. Confirm it has exactly one
   `ProductionTrainerBootstrap` component and **Production Enabled** is checked.
3. Leave `Prototype Demo` assigned to the existing `PrototypeDemo` object. That object is
   inactive in the saved scene and is also disabled by the bootstrap at runtime.
4. Create or select the local `QuestMvpCatalogAsset` generated by the content-authoring
   workflow and assign it to **Selected Catalog**.
5. Add one component for each required production port and drag it into the matching field:
   **Input Provider** (`IInputSnapshotSource`), **Registration Provider**
   (`IRegistrationStateSource`), **Safety Provider** (`IActivationSafetyPort`), and
   **Recorder Provider** (`IProcessRecorder`). A component must implement the interface
   named in parentheses.
6. Optionally assign **Snapshot Sink** (`IProcessSnapshotSink`) and **Haptics Provider**
   (`IHapticLifecyclePort`). The fallbacks only log lifecycle changes and stop no hardware.
7. Enter Play Mode. The Console must report any missing provider and the process must remain
   inhibited until every required real provider is healthy. It must never become Active with
   a missing input, registration, safety, or recorder provider.
8. Before a device build, verify that `PrototypeDemo` remains inactive and that no other
   object creates a `ProcessCoordinator`.

Platform, evaluator, recorder, UI, and haptic issues will provide the concrete components
for these fields. Until then, the intentionally missing adapters make the production scene
safe to open and test without pretending that hardware is available.

## Command flow

UI components read `ProductionTrainerBootstrap.Current` and submit requests through the
coordinator-facing command adapter added with the UI. They must not keep a second activation
state. The expected operator flow is:

`StartSession -> registration -> PrepareAttempt -> select nozzle/connect clamp -> Arm ->
Running -> FinishAttempt -> Reviewing -> retry or FinishSession`.

Pause or invalid tracking moves the attempt to `Suspended`. Re-arm is explicit. Emergency
stop has highest priority for commands sharing a timestamp, stops haptics immediately, and
requires trigger release plus an explicit reset.

## EditMode verification

In **Window > General > Test Runner**, run EditMode tests in
`WeldingTrainer.Application.Tests`. They cover registration gating, missing safety,
same-timestamp E-stop priority, registration replacement, immutable attempt selection,
retry history, explicit save failure, trigger-release re-arm, event ordering, session
completion, and teardown.
